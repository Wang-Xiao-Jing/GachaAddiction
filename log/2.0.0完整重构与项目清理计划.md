## 6. 目标职责与依赖方向

### 6.1 总体方向

~~~mermaid
flowchart TD
    Boot["启动与注册装配"] --> App["卡池及来源用例"]
    Boot --> Storage["文件与NBT适配"]
    Net["现有网络处理入口"] --> App
    Client["客户端界面与渲染"] --> Contracts["公共身份、数据和消息契约"]
    App --> Domain["奖励与执行领域"]
    App --> Ports["快照、日志、状态及投递端口"]
    Storage --> Ports
    Domain --> Contracts
~~~

图表示职责关系。按2026-10-21最新选择，API、核心、客户端、兼容和生成职责通过根工程中的Java包区分，不再建立物理Gradle子项目。具体装配入口可以知道实现；纯规则、公共身份和服务端业务仍不能反向拉入客户端实现。

- `reward`：生成、规则、数量、参数、概率和来源等领域模型。
- `execution`：执行步骤、通道、预算、预览和编排；不处理GUI或文件路径。
- `cardpool`：卡池、套餐、请求权限、确认、消费、事务和交付用例。
- `persistence`：文件、WAL、NBT和存储实现；不决定展示动画或抽奖概率。
- `presentation`：服务端演出会话、强制观看和锁的业务责任。
- `announcement`：服务端播报快照、请求校验和会话生命周期。
- `client`：本地工作区、界面、渲染、客户端播报与可选客户端适配。
- `network`：保留现有消息身份和方向，负责解码、边界检查及向业务入口分发。
- `data`：定义加载、编译、校验及快照发布；不同时充当道具工厂。
- `registry`：全局注册装配；领域中的普通Map容器或数据类型不因名称含Registry就盲目迁移。

有状态业务服务可以在包内组合小组件，对调用者保持清晰入口；不为每个步骤创建一个仅转发的接口。

- 排查从IO完成回调再次进入 `readAll().join()` 的自等待；决定快照读取、异步接口或明确执行器转移方案。
- 验收必须覆盖队列尚未完成时再次draw、失败恢复、登出和关闭，不只覆盖顺序单抽。

### B03 邮箱领取与投递持久化

- 明确WAL提交、账本进度、玩家库存/实体存档及邮箱删除各自的线性化点。
- `take` 后抛异常时补回，只能说明异常路径处理，不证明崩溃安全。
- 设计可恢复的领取/投递状态、幂等键和逐堆确认边界；数据格式变化须先确认D01及迁移策略。

- 任何可能改变真实玩家资产的故障注入须另行批准，并使用隔离数据副本。

### B04 物理端与可选依赖加载
