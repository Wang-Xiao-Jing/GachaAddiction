# 2.0.0 本地编辑、自动拿取与播报 API

> 本地保存和部署说明继续有效；协议、自动拿取时机及后续Data状态已按当前源码更新。第8节仍是原改造批次记录。当前待办和跨功能验收见[主计划](2.0.0计划.md)与[验收清单](2.0.0验收清单.md)。

更新日期：2026-10-19。目标：Minecraft 1.21.1 / NeoForge 21.1.249 / Java 21，LDLib2 2.2.39.a 可选。

## 1. 已确认的简化边界

所有定义编辑保存本机。采用原版数据包格式，服主手动把文件放到服务器后，再通过更新命令或更新按钮应用。

本轮移除在线编辑租约、心跳、接管、服务端草稿、备份恢复、在线发布和相应同步链。混合奖励、独立执行、公开卡池、奖励事务、库存与收件箱仍保留，不因移除编辑后台而删除玩家资产。

当前代码改动已经落入工作树；构建、Data、游戏和交互验收均未执行。IDE 诊断结果见末节，不以本文流程说明代替运行证据。

## 2. 本地编辑和部署

### 2.1 本地入口与目录

- 客户端安装 LDLib2 后，可从配置界面的“本地数据包编辑器”进入。
- 服务端原有 `/gacha admin workbench` 入口只通知客户端打开本地编辑器；它沿用查看管理数据的 2 级权限。
- 从配置界面编辑本机文件不需要服务端编辑权限，也不要求服务端安装 LDLib2。
- 工作台继续使用官方 Editor、EditorWindow、多标签和 Inspector；JSON 和可视编辑仍作用同一份本地缓冲。

目录相对实际游戏目录：

~~~text
config/gachaaddiction/local_datapack/
  pack.mcmeta
  data/<namespace>/gacha/<kind>/<path>.json

config/gachaaddiction/gachaaddiction_local.zip
~~~

定义种类沿用 `reward_pools`、`tables`、`execution_plans`、`card_pools`、`source_groups`、`rule_groups`、`condition_groups`、`quantity_rules`、`request_presets`。

保存写本地 JSON。关闭有未保存修改的标签时使用官方保存提示；保存失败不会继续执行关闭回调。外部文件已变化时拒绝覆盖，需重新读取或另存处理。

本地只做 JSON 根结构、大小和文件边界检查，不运行服务端世界中的奖励编译或抽取。实际语义、跨定义引用与加载是否有效，由服务端重载校验。

### 2.2 导出与手动部署

1. 保存需要保留的标签；存在未保存定义时，导出会提示先保存。
2. 选择“导出数据包”，生成本机 ZIP。
3. 服主手动将 ZIP 或完整数据包目录放到目标世界的 `datapacks` 目录。
4. 服主执行 `/gacha reload`、原版 `/reload`，或点击“更新服务器”。
5. 查看原版命令返回与服务端重载日志，确认实际成功后再使用新定义。

更新按钮只发送 `gacha reload` 命令，不上传 ZIP、不写服务器文件、不把本地未保存内容当成服务器草稿。按钮可发送请求不代表有权限，服务端会再次检查。

`/gacha reload` 使用现有 MANAGE_ADMIN 的 4 级权限，再交给原版 reload 命令处理。原版 `/reload` 自身权限规则保留。之前被明确禁用的数据包仍需按原版数据包启用流程处理，更新按钮不强制覆盖禁用设置。

界面设计器仍保存本地 `.ui.nbt`；模板、样式和纹理属于客户端资源包。数据包导出不把客户端 UI 资源混入服务端定义。

代码入口：[GachaLocalWorkspace.java](../src/main/java/xiaojin/gachaaddiction/client/GachaLocalWorkspace.java)、[GachaLocalDocumentState.java](../src/main/java/xiaojin/gachaaddiction/client/GachaLocalDocumentState.java)、[LDLib2LocalEditorScreen.java](../src/main/java/xiaojin/gachaaddiction/client/compat/ldlib2/LDLib2LocalEditorScreen.java)、[LDLib2LocalDefinitionEditor.java](../src/main/java/xiaojin/gachaaddiction/client/compat/ldlib2/LDLib2LocalDefinitionEditor.java)。

## 3. 已移除的冗余功能

### 3.1 移除结果

本轮删除 39 个旧类：13 个服务端编辑模型/服务、15 个旧编辑网络载荷、1 个发布重载包装、2 个服务端草稿/发布存储实现、8 个旧后台页面或协调类。

旧消息的 15 项注册、登录时的编辑能力声明、退出时的租约处理、服务端草稿初始化与 published 自动迁移也已移除。服务端不会因打开本地编辑器而保存、恢复或发布定义。

以下部署功能因此不再存在：

| 旧功能 | 新方式 |
|---|---|
| 单人编辑租约、心跳、续租、接管 | 每名作者编辑自己的本机文件 |
| 服务端 current/backup/recovery 草稿 | 本地文件、未保存提示和外部修改检查 |
| 摘要/文档请求与保存回包关联 | 本地工作区直接读写 |
| 在线发布、发布排期、回滚接口 | 服主手动放文件后执行原版重载 |
| 在线卡池启停/文档修改 | 修改本地定义并重新部署 |
| 工作台的资源包发送页 | 本地界面资源编辑；原有服务端手动资源包命令仍保留 |
| 多套旧后台编辑壳和无引用的旧可视编辑类 | 一个本地 Editor 工作台，复用现有 Inspector 与 JSON 控件 |

旧世界中已经存在的 drafts、published、migration 标记等文件**没有删除**。不再自动加载、迁移或发布这些旧编辑存储；已经部署到世界 `datapacks` 的数据包仍按原版规则加载。需要保留的旧内容应由服主自行备份并迁出为标准数据包，不假定本轮已替旧存档完成转换。

### 3.3 其他可继续精简的候选，本次未删除

| 候选 | 可以减少的复杂度 | 本次保留原因 |
|---|---|---|
| 无公开卡池时仍启动事务运行时 | 可考虑按需启用 WAL、快照、参数仓储和投递账本 | 需要另定启用条件和存档恢复规则，不能随意丢弃未完成资产事务 |
| 通用 JSON Inspector 与跨文件自动改名 | 如果只使用少量固定模板，可缩小任意结构编辑和扩展引用识别范围 | 属于现有编辑能力，未擅自降为只支持少数固定字段 |
| 请求预设与执行计划的多个入口 | 若实际使用只需一种入口，可进一步收敛对外模型 | 原有独立轻量调用和脚本入口需要保留，不能只按未使用警告删除 |
| 概率结构描述命令与高级预览 | 普通使用可能只需结果展示，不需要完整结构说明 | 当前是可选、按调用执行的调试能力，不是持续运行的后台任务 |
| 动态资源包推送命令 | 固定资源包场景可交给原版服务器资源包配置 | 对指定目标临时发送仍有用途，本次没有删除原有命令 |
| 历史翻译键与历史用例 | 可在发布前确认实际引用后清理 | 生成资源与历史记录未做无关批量清理，不用“未引用”替代兼容范围判断 |

不再继续扩展在线审计后台、版本发布管理、排程、服务器文件上传或资源托管。此次精简集中在编辑/部署链，奖励核心的可靠性问题仍按原审计另行处理。

## 4. 自动拿取

### 4.1 客户端判定

命中以下任意一项即为候选：

- 命中现有客户端 `gachaa_screen.whitelist_filter_list`；
- [RarityUtil](../src/main/java/xiaojin/gachaaddiction/util/RarityUtil.java) 返回的等级达到客户端 `gachaa_screen.minimum_reward_rarity`。

最低等级默认 RARE 的 ordinal，即 2；可配置为其他等级，沿用 Confluence Magic Lib / RarityCore / 原版的既有判定顺序。空白名单不会匹配全部物品。

动画黑名单仍只负责原有展示筛选，不自动成为自动拿取的否决条件。

### 4.2 Common 开关独立生效

| 配置 | 默认 | 读取方 | 意义 |
|---|---|---|---|
| COMMON `auto_take.enabled` | false | 本地客户端 | 当前玩家是否发送自动拿取请求 |
| COMMON `auto_take.allowed` | true | 逻辑服务端 | 是否接受该类请求 |
| CLIENT `gachaa_screen.minimum_reward_rarity` | 2 | 本地客户端 | 最低候选稀有度，与白名单按“或”匹配 |

COMMON 不作为服务端同步配置覆盖客户端。同一进程的单人游戏也用两个不同字段分别表达本地意愿和逻辑服务端许可。

仅修改客户端的 `allowed` 不会改变远程服务器的许可；仅修改服务端的 `enabled` 也不会替玩家开启自动拿取。关闭任意必要一侧，均不执行本轮新增的自动移动。

### 4.3 动画时机

[GachaRewardPhase.java](../src/main/java/xiaojin/gachaaddiction/api/client/GachaRewardPhase.java)定义 OPEN 与 COMPLETE：

- OPEN：打开流程收到真实奖励条目时触发，尽早请求拿取，不等动画结束。
- COMPLETE：对应转轮揭晓时触发；跳过动画也触发这次完成通知。
- 当前真实容器默认只在OPEN请求自动拿取。COMPLETE仍是揭晓通知/扩展阶段，动画实现可覆盖 [BasicGachaScreen.getAutoTakePhases()](../src/main/java/xiaojin/gachaaddiction/client/gui/screen/BasicGachaScreen.java)，不等于默认再次拿取。
- 每个屏幕按时机记录已经请求的槽位，避免同一阶段因刷新、重复回调反复提交。
- 只有显式启用COMPLETE的扩展才会在完成阶段再次尝试；已移走内容仍须通过当前槽位和服务端快照核对。
- 配置预览沿用 ReelHost 的空完成回调，不产生网络请求。

只在完成时尝试的Java扩展示意（类内部方法片段，不是独立编译单元）：

~~~text
@Override
protected Set<GachaRewardPhase> getAutoTakePhases() {
    return Set.of(GachaRewardPhase.COMPLETE);
}
~~~

### 4.4 服务端执行和物品去向

客户端只发送菜单 ID、槽位 ID 和所见物品快照。[GachaAutoTakePayload.java](../src/main/java/xiaojin/gachaaddiction/network/GachaAutoTakePayload.java)在服务端线程核对：

1. 服务端独立许可已开启，玩家不是旁观者；
2. 当前菜单仍匹配、可访问，并且是已标记的抽奖容器；
3. 槽位存在、不属于玩家自身库存，玩家允许从该槽位拿取；
4. 服务端物品与请求快照的种类、组件和数量一致。

通过后使用当前菜单的 `quickMoveStack` 移动服务端真实物品，并进行正常槽位同步。不会根据客户端发来的 ItemStack 创建奖励。背包放不下的部分沿用菜单逻辑留在原容器，不增加掉落或邮箱分支。

没有另造自动拿取成功回执，结果以正常容器/玩家库存同步为准。未协商新可选通道时，客户端不发送请求；服务端拒绝时物品保持原处。

本轮新增的自动拿取针对仍在真实容器中的奖励。FTB/物品袋等已经发放到背包的展示不再发一次；公开卡池原有 INVENTORY / DROP / INBOX 等投递方式保持原语义，没有把收件箱领取改成新的自动事务。

客户端入口：[GachaRewardClientUtil.java](../src/main/java/xiaojin/gachaaddiction/util/client/GachaRewardClientUtil.java)；动画完成回调：[ReelHost.java](../src/main/java/xiaojin/gachaaddiction/api/client/ReelHost.java) 与 [VerticalReelWidget.java](../src/main/java/xiaojin/gachaaddiction/client/gui/widget/VerticalReelWidget.java)。

## 5. 稀有物品播报

后续实现已接入客户端请求、服务端核对转发、聊天栏、右上角提示、屏幕中上方滚动条及 Alt 手动入口，详见 [2.0.0开箱播报.md](2.0.0开箱播报.md)。

发送者按本地稀有度或白名单选择每次最稀有的最多 3 种物品；接收者独立选择显示方式。无结构时使用维度名称。可播报的真实容器奖励槽位显示 0.3 透明度的淡绿色背景边框，Alt只在当前会话界面生效，真正退出后清空快照。实现合同为 [IGachaAnnouncementApi.java](../src/main/java/xiaojin/gachaaddiction/api/IGachaAnnouncementApi.java)，接收方法改为 receive(GachaAnnouncement)。

本文件第 8 节的诊断和操作记录保留为本地编辑改造当时的结果；新增播报实现、接入范围和未执行用例以独立播报文档为准。
