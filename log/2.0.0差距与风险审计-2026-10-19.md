## 4. 代码与功能问题

优先级 P1 表示建议在扩大使用或宣布对应能力完成前处理；P2 表示后续收尾。优先级是本次建议，不是 IDE 警告级别。

### C01 · P1 · 矿车容器通配 Mixin 与目标签名不一致

- **证据：IDE 错误 + 当前依赖源码。** [setLootTable* 注入](../src/main/java/xiaojin/gachaaddiction/mixin/entity/AbstractMinecartContainerMixin.java#L57)使用 ResourceKey 和 CallbackInfo。
- 当前目标类不仅有 setLootTable(ResourceKey)，还有 setLootTable(ResourceKey,long) 和 setLootTableSeed(long)。通配选择范围与这个参数捕获签名不一致。
- IDEA 报错为“Method signature does not match expected signature for Inject”。
- **影响：** 原有矿车战利品兼容存在注入失败风险；本次没有启动游戏，不能声称已观察到启动崩溃。
- **后续计划：** 根据真实需要明确方法描述符，分别处理必要重载；保留既有战利品记录行为，再读取 Mixin 诊断。

### C02 · P1 · 矿车自定义状态的保存、读取方向写反

- **证据：静态确定。** [addAdditionalSaveData 回调](../src/main/java/xiaojin/gachaaddiction/mixin/entity/AbstractMinecartContainerMixin.java#L65)从输出 tag 读取开关，[readAdditionalSaveData 回调](../src/main/java/xiaojin/gachaaddiction/mixin/entity/AbstractMinecartContainerMixin.java#L74)反而向输入 tag 写开关。
- 当前 MC 源码中 addAdditionalSaveData 是保存路径，readAdditionalSaveData 是读取路径。
- **触发：** 已生成过战利品、依赖自定义开关的矿车保存并重新加载；保存 tag 缺少该键时还会把内存开关设为 false。
- **影响：** 对应 UI 状态不能按既定意图持久化。不是所有矿车都必然失效，仍有当前 lootTable 的兜底判断。
- **后续计划：** 纠正存读职责，并安排“生成战利品后保存/加载”的专门回归；先处理 C01，使运行验证具备前提。

### C03 · P1 · 日常恢复可能回滚正在执行的事务

- **证据：完整调用链静态推导，未运行复现。** [每次 draw 先 recover](../src/main/java/xiaojin/gachaaddiction/cardpool/GachaServerRuntime.java#L195)；[恢复器读取全部历史](../src/main/java/xiaojin/gachaaddiction/cardpool/transaction/GachaTransactionRecovery.java#L41)；[PREPARED/RESERVED/REWARD_COMPUTED 均判回滚](../src/main/java/xiaojin/gachaaddiction/cardpool/transaction/GachaTransactionHistory.java#L24)。
- [正常事务](../src/main/java/xiaojin/gachaaddiction/cardpool/transaction/GachaTransactionCoordinator.java#L57)在异步 WAL 阶段之间持续执行；恢复队列只串行化恢复，没有覆盖正常事务的整个生命周期，也没有共享的活跃事务排除条件。
- **允许出现的时序：** A 写入 PREPARED 后等待刷盘/主线程后续步骤；B 发起抽取并恢复；B 把 A 判为待回滚；A 又继续 RESERVED 或后续步骤。
- commitEligibility 的玩家筛选只在 COMPLETE_COMMIT 分支使用，不能阻止其他玩家的中间态被回滚。
- **影响：** 可能造成消费回滚与正常提交交错、重复终态或非法 WAL 转移；实际后果取决于时序和消费处理器。
- **后续计划：** 划分启动恢复与日常重试，统一协调活跃事务和恢复范围；不能仅给 recover 方法增加 synchronized 就认为覆盖了异步事务。

### C04 · P1 · 排队恢复存在日志线程自等待路径

- **证据：线程与 Future 链静态推导，未运行复现。** [恢复串联](../src/main/java/xiaojin/gachaaddiction/cardpool/GachaServerRuntime.java#L181)使用非 Async 的 handle/thenCompose；[readAll](../src/main/java/xiaojin/gachaaddiction/persistence/GachaFileTransactionJournal.java#L85)向唯一 ioExecutor 提交任务后 join。
- [WAL 完成回调](../src/main/java/xiaojin/gachaaddiction/persistence/GachaFileTransactionJournal.java#L125)在该 I/O 线程上完成 Future。
- **触发条件：** 一个恢复链需要追加终态，后面已有恢复请求排队，并且最后一步在 I/O 线程完成；后续 thenCompose 可在同一线程进入下一次 recover。
- **影响：** 下一次 readAll 把读取任务排到自己后面并阻塞等待，形成自等待。没有待恢复记录时，不能据此断言每次抽奖都会死锁。
- **后续计划：** 明确恢复任务的执行器与线程边界，移除对同一单线程执行器的阻塞提交；保留 Minecraft 世界操作的主线程约束。

### C05 · P1 · 收件箱领取存在“先删除、后发奖”崩溃窗口

- **证据：静态确定窗口，未做故障注入。** [take](../src/main/java/xiaojin/gachaaddiction/persistence/GachaFileRewardInbox.java#L111)读取后立即删除条目；[claim](../src/main/java/xiaojin/gachaaddiction/cardpool/delivery/GachaRewardInboxClaim.java#L17)随后才逐堆加入库存或掉落。
- 异常处理能恢复尚未交付内容，但进程退出或断电不会执行 catch。
- **影响：** 删除成功到实际投递、玩家存档确认之间，奖励缺少持久的领取进度凭据，可能丢失。
- **后续计划：** 先明确 claim 的持久化领取意图、完成确认与恢复协议，再实现；单纯交换两句代码会引入重复领取窗口，不能作为完整方案。

### C06 · P1 · 在线发奖进度与玩家/实体存档缺少共同确认点

- **证据：静态确定跨存储窗口，实际恢复结果未运行复现。** [deliverOnline](../src/main/java/xiaojin/gachaaddiction/cardpool/transaction/GachaPlayerRewardDeliveryHandler.java#L125)先改库存或生成实体，再将 remainderCounts 写账本。
- **丢失窗口：** 物品已加入内存库存、remainderCounts 已持久化为 0，但玩家文件尚未保存；崩溃重登后旧库存不含物品，恢复逻辑却可能只按“剩余数量 0”补偿。
- [pendingRewards](../src/main/java/xiaojin/gachaaddiction/cardpool/transaction/GachaPlayerRewardDeliveryHandler.java#L202)及 [reconcilePlayer](../src/main/java/xiaojin/gachaaddiction/cardpool/transaction/GachaPlayerRewardDeliveryHandler.java#L260)需要与实际玩家存档标记共同核对。反方向的存档/账本不一致也存在重复投递风险。
- 声明 IDEMPOTENT_BY_TRANSACTION、记录逐堆进度或捕获普通异常，都不能单独证明跨玩家文件和实体存档恰好交付一次。
- **后续计划：** 以玩家保存确认和投递账本状态共同设计恢复策略，分别处理库存、掉落、离线和溢出；与 C05 一起审定协议，但保留现有物品去向语义。

## 5. 隐藏性能问题与扩展风险

以下复杂度来自调用结构。没有采样 CPU、磁盘延迟、TPS、帧率或 GC，因此不提供“已卡顿多少毫秒”等测量结论。

### P01 · P1 · 每次抽奖重新规划整个历史 WAL

[draw 前恢复](../src/main/java/xiaojin/gachaaddiction/cardpool/GachaServerRuntime.java#L195)会进入 [readAll + histories](../src/main/java/xiaojin/gachaaddiction/cardpool/transaction/GachaTransactionRecovery.java#L46)。[规划器](../src/main/java/xiaojin/gachaaddiction/cardpool/transaction/GachaTransactionRecoveryPlanner.java#L13)重新排序、分组和校验全部记录；DELIVERED 也会进入 RESTORE_STATE，而不是直接跳过。

日志记录常驻内存，readAll 还会复制列表；这里不是每次从磁盘重读整个 WAL，但仍有随历史规模增长的复制、排序、解码和回放成本。玩家谓词没有在规划阶段缩小输入。

以历史记录数 N 计，单次至少线性扫描，规划包含排序，存在 O(N log N) 工作；持续运行的累计工作会超线性增长。启动时还需一次性读取全部 WAL。

**计划：** 启动恢复与日常未完成事务索引分离，增加受一致性约束的 checkpoint/归档机制。不能直接删除旧日志，否则状态回放和幂等依据会丢失。

### P02 · P1 · 每个奖励堆都重写完整投递账本并强制刷盘

[逐堆投递](../src/main/java/xiaojin/gachaaddiction/cardpool/transaction/GachaPlayerRewardDeliveryHandler.java#L128)每处理一堆调用 store；[账本 write](../src/main/java/xiaojin/gachaaddiction/persistence/GachaFileRewardDeliveryLedger.java#L108)每次重新编码全部奖励、进度、返回奖励，并执行 force(true) 和文件替换。

S 个奖励堆对应 S 次进度写入，以及准备/应用/完成等额外写入。单次编码本身与奖励列表规模有关，进度阶段可产生接近 O(S²) 的序列化工作，并有 O(S) 次刷盘。

这些操作位于服务端效果执行路径；WAL 使用异步线程和 group commit，不代表这份独立账本已经异步化或合并刷盘。

**计划：** 先解决 C06，再设计增量进度日志、提交粒度和有界批次。不能为减轻 I/O 直接去掉持久化步骤。

### P03 · P1 · 参数状态保存成本随所有历史事务增长，并最终触及文件限额

[commitPrepared](../src/main/java/xiaojin/gachaaddiction/persistence/GachaFileParameterStateRepository.java#L153)把每个事务 ID 加入 appliedTransactions，即使没有实际状态字段更新，也会保存。

[encode](../src/main/java/xiaojin/gachaaddiction/persistence/GachaFileParameterStateRepository.java#L306)重新排序并写入全部参数值及全部已应用事务 ID，再 force(true)。默认最大参数文件为 64 MiB，不是总历史事务数上限管理方案。

**影响：** 单次提交耗时、分配量、状态文件体积持续增长；超过大小限制后新的提交会失败。当前代码未见配套压缩/历史裁剪协议。

**计划：** 设计与 WAL checkpoint 一致的已应用水位或分片存储，保留正确的去重边界。不要独立过期或清空事务 ID。

### P04 · P2 · 同一定义在准备、确认和执行时重复编码并校验磁盘快照

[prepare](../src/main/java/xiaojin/gachaaddiction/cardpool/GachaPublicCardPoolEndpoint.java#L64)、[confirm](../src/main/java/xiaojin/gachaaddiction/cardpool/GachaPublicCardPoolEndpoint.java#L80)与 [draw](../src/main/java/xiaojin/gachaaddiction/cardpool/GachaCardPoolService.java#L85)均调用快照存储。

[store](../src/main/java/xiaojin/gachaaddiction/persistence/GachaCardPoolSnapshotStore.java#L24)没有在编码前复用已有哈希；[archive.store](../src/main/java/xiaojin/gachaaddiction/persistence/GachaFilePoolSnapshotArchive.java#L46)在文件已存在时还会完整读取旧文件校验。

一次正常的准备—确认流程通常会触发三次该路径。已有文件不会每次重新落盘，但仍重复编码、哈希和读文件。

**计划：** 按不可变定义/重载版本缓存编码和哈希，定义变更时失效；保留公开确认与实际执行之间的快照一致性检查。

### P05 · P1 · 收件箱全量扫描并整包发送，超过协议计数会无法正常展示

[pending](../src/main/java/xiaojin/gachaaddiction/persistence/GachaFileRewardInbox.java#L94)读取玩家目录所有条目；[邮箱请求](../src/main/java/xiaojin/gachaaddiction/network/RequestRewardInboxPayload.java#L27)和 [领取后刷新](../src/main/java/xiaojin/gachaaddiction/network/ClaimRewardInboxPayload.java#L51)均发送整个结果，没有分页。

[协议限额](../src/main/java/xiaojin/gachaaddiction/network/GachaRewardInboxCodecs.java#L13)对条目数和每条奖励堆数都设置 4096；[完整列表编码](../src/main/java/xiaojin/gachaaddiction/network/OpenRewardInboxPayload.java#L20)受该限额约束。当前 MC 的 ByteBufCodecs.collection 在编码时检查 maxSize。

**影响：** 历史积压增加主线程文件读取和 NBT 解码，领取一次也重扫全量；超过列表或单条奖励堆限制时会产生编码失败。计数限制也不等于整个载荷的字节预算。是否断开连接等后果本次未实测。

**计划：** 分页元信息、按条领取、增量刷新、总字节预算；使磁盘可存数据范围与网络可展示范围一致，并提供明确失败反馈。

### P06 · P2 · 每个玩家登录会重建整个战利品展示缓存

[OnDatapackSyncEvent 处理](../src/main/java/xiaojin/gachaaddiction/event/Events.java#L113)无条件调用 [reload](../src/main/java/xiaojin/gachaaddiction/util/LootDisplayCache.java#L22)，后者清空并遍历整个战利品表注册表、重新抽取展示条目。

当前 NeoForge 21.1.249 源码明确该事件也在玩家加入时触发，所以缓存成本不只发生在数据包重载时。

**计划：** 在真实数据重载时重建，单玩家同步复用对应版本的缓存；保留初次启动和定义变更后的刷新。

### P07 · P2 · Inspector 每 tick 为每个引用字段重建并排序候选

[文档 tick](../src/main/java/xiaojin/gachaaddiction/client/compat/ldlib2/LDLib2AdminDraftDocumentScreen.java#L53)调用 refresh；[引用刷新](../src/main/java/xiaojin/gachaaddiction/client/compat/ldlib2/LDLib2AdminJsonInspector.java#L114)对每个引用字段遍历 summary.documents、筛选、转换、排序和构建列表，然后才比较是否变化。

因此“没有变化就不 setCandidates”只节省后续更新，没有节省候选列表生成。引用字段数 R、文档数 D 增长时，tick 成本可接近 R 次 D 规模的扫描/排序。

此外原始 JSON 每次编辑都会经过限额检查和解析，结构变化时重建 Inspector；其延迟是否可感知需实际测量。

**计划：** 按摘要版本和定义种类缓存候选列表；只对确实变化的内容刷新，保留非法输入和本地缓冲保护。

### P08 · P2 · 保存单个文档会重复读取全量草稿并同步编译整个定义集

当前合法保存链中，请求读取当前草稿（历史位置：`../src/main/java/xiaojin/gachaaddiction/network/SaveAdminDraftDocumentPayload.java#L81`，当前文件已移除）、setDraftDocument（历史位置：`../src/main/java/xiaojin/gachaaddiction/admin/GachaAdminService.java#L158`，当前文件已移除）、saveDraftRevision 的版本复核、saveRevision（历史位置：`../src/main/java/xiaojin/gachaaddiction/persistence/GachaFileDraftStore.java#L131`，当前文件已移除）再次 current()，构成多次全量读取。

read（历史位置：`../src/main/java/xiaojin/gachaaddiction/persistence/GachaFileDraftStore.java#L253`，当前文件已移除）每次读取完整 NBT；保存前校验（历史位置：`../src/main/java/xiaojin/gachaaddiction/admin/GachaAdminService.java#L172`，当前文件已移除）重新解析和编译全部文档，随后写 current、backup 等文件。网络入口通过 enqueueWork 执行，因此位于服务端任务路径。

**影响：** 少量定义时可能很轻；大型草稿保存可能阻塞服务端。默认 64 MiB 的单快照限额不能保证交互耗时合理。这里不能将 synchronized 理解成自动后台执行。

**计划：** 单次操作复用同一个不可变版本快照，保持版本和原子保存校验；将可安全脱离世界状态的工作按明确顺序调度。不要简单删除重复校验而削弱一致性。
