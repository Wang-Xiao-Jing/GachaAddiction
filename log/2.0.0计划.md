版本更新记录见 [2.0.0 更新日志](2.0.0.md)，具体交互与回归用例见 [测试计划](测试.md)。

## 2. 当前优先任务：本地编辑器与数据包部署

### 2.1 官方工作台接入

- [x] 参照 LDLib2 2.2.39.a 的 `/ldlib2_ui_editor` 命令打开的完整编辑器，不以模板加载界面或单独嵌入 `UIEditorView` 代替。
- [x] 能复用的官方实现直接复用；需要业务差异时优先继承、扩展或适配，无法满足需求的部分才局部复制改造，不默认复制整套编辑器源码。
- [x] 抽卡设计器接入官方 `UIEditor`、`EditorWindow` 与 `UIEditorView`，保留完整层级、画布、属性、样式及资源编辑流程，只适配抽卡业务绑定与安全限制。
- [x] 整个后台使用官方 `Editor` 工作台与业务 `View`，复用官方停靠、分割、标签、Inspector、资源面板及悬浮窗口体系。
- [x] 将当前手写后台布局及独立页面流程迁入该工作台，业务适配优先通过官方扩展点完成，不继续扩展自制编辑器外壳。
- [x] 主入口集中提供本地定义编辑、数据包导出、界面设计与服务器更新；不建设在线发布或运营后台。
- [x] 复用 LDLib2 底层控件、布局、样式、资源容器与资源值接口，必要时增加业务适配，避免覆盖官方包名、注册器及已有资源格式。
- [x] 纹理等属性的资源选择弹窗直接复用官方组件；只有无法满足具体业务需求时才改造，不为统一外观额外复制底层配置器或添加 Mixin。
- [x] 局部源码复制仅限官方扩展点无法满足需求的最小范围，说明必要原因并记录上游版本、来源、许可证与修改；不复制无关 `SceneEditor`、`NodeGraph` 或整个 LDLib2。

### 2.2 本地保存、部署与界面状态

- [x] 每名玩家独立编辑本机文件，不再需要编辑租约、心跳、接管或服务端草稿。
- [x] 定义保存到本地原版数据包目录；界面模板与样式保持客户端资源包边界。
- [x] 本地保存和导出都不改变服务端；服主必须手动放置数据包，再执行 `/gacha reload`、原版 `/reload` 或点击更新按钮。
- [x] 更新按钮只发送重载命令，权限由服务端重新检查，不上传或代写服务器文件。
- [x] 保留未保存提示、外部文件冲突保护、关闭返回及文件操作失败反馈。
- [x] 保留可选的编辑器打开通知，移除摘要、文档、编辑、发布、恢复等旧同步消息；当前主协议为4，本地化阶段的3已由分轮结果协议取代。
- [x] 本地编辑器仅需客户端安装 LDLib2，不再要求服务端安装 LDLib2。

## 3. 功能计划

### 3.1 混合奖励池与轻量调用

- [x] 保留奖励核心的兼容、数据格式和调用入口；旧服务端在线编辑协议按本轮简化范围移除。
- [x] 一个奖励池组合多个原版/自定义战利品表及分阶段结果规则，主体见`GachaHybridRewardPool`和定义编译器。
- [x] 候选与自定义来源支持条件、动态权重及保底规则；组合正确性仍需CORE用例验收。
- [x] 通过`GachaVanillaLootCondition`及规则条件类型接入原版形式和扩展条件。
- [x] 原版来源生成后交由规则处理逻辑奖励，不改被引用的原版表定义。
- [x] 外部参数进入`GachaRewardPoolRequest`及参数编辑器，奖励池自身不持久化保底或条目状态。
- [x] 调用方可传轮数，数量与最终成品堆由外层执行和数量规则处理。
- [x] 奖励池、直接来源、规则组和数量规则可通过独立执行层使用。
- [x] 卡池作为公开入口包装，`/gacha test`保留为实际投递奖励的测试命令。
- [x] 已接入库存消费、投递及收件箱；持久化一致性风险单列第5.3节，不能视为已验收安全。

### 3.5 自动拿取与开箱播报

- [x] 客户端使用现有白名单，或通过 RarityUtil 达到可配置的最低等级；默认 RARE（2）及以上。
- [x] 原版容器仅在OPEN请求自动拿取；新增专用道具在演出完成后由服务端事务统一消耗和发放，预览不产生真实抽奖请求。
- [x] COMMON 中的本地自动拿取开关与逻辑服务端许可独立读取，不互相同步。
- [x] 服务端核对当前菜单、槽位和实际物品后执行移动；背包不足部分保留在容器。
- [x] 接入发送者筛选、服务端实际奖励核对及聊天、右上角提示、中上方滚动条；接收者独立开关，每次最多播报最稀有的3种。
- [x] 结构名无法识别时显示维度名；保留箱子原名和重命名，物品名称支持完整悬浮详情。
- [x] 当前开箱界面悬浮已揭晓奖励按 Alt 手动播报；真实容器奖励槽位显示透明度0.3的淡绿背景边框，动画返回同一容器时保留快照，真正退出后清空。
- [x] 右上角使用原版 Toast 的滑入滑出、提示音、共享排位和通知时长倍率；中上方保持独立滚动，两者的物品图标及数量在文字末尾最后绘制。
- [x] 从原版进度提示复制两份独立背景，分别支持资源包替换 PNG 与 GUI sprite 缩放元数据。
- [x] 资源包 JSON 沿用黑白名单条件匹配稀有度、物品、标签和组件/NBT，两种背景分别取第一条命中的有效目标。
- [x] 多个资源包的同路径规则列表合并，按包优先级从高到低、包内从上到下匹配；未命中时继续查找，提示缓存选择结果并随规则重载更新。

## 5. 执行顺序与验收

### 5.1 执行顺序

1. 核对命令打开链、官方扩展点与现有业务差异，逐项确定直接复用、继承适配或必要局部改造的范围。
2. 使用官方编辑器承载本地定义与界面编辑，完成原版数据包导出及服主手动重载链。
3. 处理必要局部改造、配置预览、翻译及兼容细节。
4. 通过 IDEA 核对修改范围内的错误、警告、类型、引用与导入，不处理无关诊断。
5. 将交互与回归场景补充到 [测试计划](测试.md)，按另行授权的范围执行验收并记录实际结果。
