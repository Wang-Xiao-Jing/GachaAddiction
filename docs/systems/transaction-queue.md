# 事务恢复与抽奖队列

GachaServerRuntime 为启动恢复、登录恢复、在线抽奖和邮箱领取共用一个 GachaTransactionQueue。每次 draw 把“恢复该玩家未完事务，再执行本次抽奖”作为同一个队列任务提交；后续恢复和领取不能插入两段之间。领取开始前再次核对在线玩家实例，登出或重新连接前的旧实例不能继续领取。

## 队列位置与重入

submit 在同步块内先保存前驱并把自己的完成状态设为队尾，再调用执行器。执行器可能立即运行任务；任务内部再次提交时也只能排到已经保留的位置之后。原来先调用 thenComposeAsync、后赋值队尾的写法，无法覆盖这种内联重入。

任务失败会通过原结果报告，但归一后的队尾仍允许后续任务执行。返回 minimalCompletionStage，调用方取得的 CompletableFuture 只是观察副本；取消或手动 complete 该副本不能提前解除实际任务占用的位置。只有操作返回的 CompletionStage 真实结束后才能继续。

队列只负责调度，不拥有事务数据、WAL、玩家或存档。WAL 仍由 GachaFileTransactionJournal 管理，投递仍由既有账本及邮箱管理，没有新增平行事务状态或持久化来源。

队列同时包装主线程 Executor，协调器、恢复器和运行时后续回调通过此入口调度。close 先关闭接收，令未完成观察结果失败，阻止尚未开始的队列任务和主线程状态回调，再关闭 WAL；不等待服务器主线程上的自身回调，也不取消或回滚已经记录的持久化意图。未完意图留待下次启动恢复。

## 实际检查

Transaction Queue Regression Checks 最后于 2026-10-21 通过 IDEA Application 配置执行，exitCode=0。七组检查覆盖：

- 内联执行器中，活跃抽奖内再次提交恢复；恢复必须等待抽奖完成。
- 手动执行器中，恢复尚未完成、draw 尚未完成和下一次恢复的完整顺序。
- 返回失败阶段及同步抛异常后，下一任务仍能完成，原异常继续报告。
- 调用方取消或伪造观察 Future 的完成，不得影响未完成的真实抽奖和后续恢复。
- 关闭时结束活跃及排队观察者，保留真实持久化操作；迟到完成不能改写关闭结果。
- 关闭前已调度但尚未开始的操作不能执行。
- 关闭前已排入主线程的状态回调不能执行，关闭后执行器拒绝新回调。

上述检查不启动游戏，不修改玩家资产或现有存档。最终 Java 编译通过；统一分析及修正复查见 verification-20261021.md，不用旧批次诊断数量冒充当前全项目统计。
